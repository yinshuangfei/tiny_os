### 在 scheduler 函数中，在一个时间片内，一个核心持有 p->lock 锁，并在执行 swtch 的过程中，这时其他核遍历 proc 数组中正好遍历到这个 p, 在 acquire 时会被阻塞吗?
会被阻塞。
当 CPU 核心 A 持有进程 p 的 p->lock 并执行 swtch 时，如果 CPU 核心 B 在遍历 proc 数组时正好选中了这个进程 p，并尝试调用 acquire(&p->lock)，核心 B 确实会被阻塞（自旋等待），直到核心 A 完成切换并释放这把锁。
当 swtch 执行完毕，核心 A 实际上已经变成了进程 p。进程 p 在恢复执行后的第一件事，就是调用 release(&p->lock)。
虽然核心 B 会被阻塞，但等待的时间极其短暂。

### 如果我们把 xv6 运行时的栈做一个完整的梳理，它们分别是：
- User Stack：用户程序的函数调用栈（每个进程一个）。
- Kernel Stack：进程陷入内核时的执行栈（每个进程一个，映射到内核页表上）。
- Scheduler Stack：调度器挑选进程时的执行栈（每个 CPU 核心一个）。
- Interrupt Stack：响应硬件中断时的执行栈（每个 CPU 核心一个，即 struct cpu 中的 kstack）。
- Boot Stack：内核启动初期的临时栈（仅 CPU 0 使用）。

### 用户态的栈，从用户态 trap 到内核态的栈，以及 sche 的栈，有什么关系？
- 用户态栈 (User Stack)：位于进程的用户虚拟地址空间中（通常在堆的上方，向下增长）。它专门用于保存用户态程序的函数调用链、局部变量等。当进程运行在用户态时，CPU 的栈指针（sp）指向这里3。
- 进程的内核栈 (Kernel Stack)：位于内核虚拟地址空间中（通常在 Trampoline 蹦床页下方）。每个进程都有一个独立且专属的内核栈。当进程陷入内核态（如系统调用、中断）时，CPU 的栈指针会切换到这个内核栈35。
- 调度器的栈 (Scheduler Stack)：位于内核虚拟地址空间中。它不是属于某个特定进程的，而是每个 CPU 核心专属的（属于 struct cpu 结构体的一部分）。它专门用于执行该核心上的调度器线程（scheduler thread）

- 阶段一：用户态栈 → 进程的内核栈
当用户进程因为系统调用（ecall）或中断陷入内核态时，硬件和 trampoline 汇编代码会协同工作，完成第一次栈的切换：
硬件将特权级从用户态提升为内核态。
内核代码（uservec）会将当前所有的用户态寄存器（包括用户栈指针 sp）保存到当前进程的 trapframe 中。
CPU 的栈指针（sp）被切换为该进程专属的内核栈。
- 阶段二：进程的内核栈 → 调度器的栈
当内核决定当前进程需要让出 CPU（例如主动调用 yield/sleep，或被时钟中断强制抢占）时，会执行 swtch 函数，完成第二次栈的切换：
swtch 会将当前进程内核栈上的关键寄存器（如 ra, sp, s0-s11）保存到该进程的 struct context 中。
swtch 从目标 CPU 的调度器 struct context 中恢复寄存器，并将 CPU 的栈指针（sp）切换为调度器的栈。
- 阶段三：调度器的栈 → 新进程的内核栈 → 新进程的用户态栈
当调度器选定了下一个进程（例如进程 B）后：
swtch 将调度器的栈切换为进程 B 的内核栈，并恢复进程 B 的内核寄存器。
进程 B 的内核代码继续执行，最终通过 usertrapret 和 trampoline（userret）恢复保存在 trapframe 中的用户态寄存器。
执行 sret 指令，CPU 特权级降为用户态，栈指针（sp）恢复为进程 B 的用户态栈，继续执行用户代码

# 实时内核的特点是什么?
实时内核的核心目标与通用操作系统不同：通用系统追求的是“平均吞吐量”和“整体公平”，而实时内核追求的是“最坏情况下的延迟（Worst-Case Latency）”和“时序的可预测性”。
- 1. 内核的完全可抢占性（Full Preemption）
在普通内核中，即使开启了抢占，内核在执行某些关键代码段（如持有自旋锁 spinlock 时）也是不可抢占的，这会导致高优先级任务被阻塞。
实时内核特点：将内核中大量的自旋锁（spinlock）替换为可休眠的互斥锁（rt_mutex）4。这意味着，即使当前内核线程持有锁，如果来了一个更高优先级的实时任务，当前任务会被迫“休眠”并让出 CPU，高优先级任务可以立即抢占执行。这极大地减少了内核态的调度延迟。
- 2. 中断线程化（Interrupt Threading）
在普通内核中，硬件中断触发后，中断服务程序（ISR）会立即打断当前任务，且 ISR 执行期间通常是不可抢占的。如果 ISR 处理时间过长，会导致严重的延迟。
实时内核特点：将绝大部分中断处理程序（包括硬中断和软中断）转换为普通的内核线程。这些中断线程和普通进程一样受调度器管理。如果中断线程优先级较低，它可以被高优先级的实时任务抢占；同时，开发者可以灵活调整中断线程的优先级和 CPU 亲和性（绑定到特定核心），从而保证关键中断不被干扰。
- 3. 严格的优先级调度与优先级继承（Priority Inheritance）
普通内核的默认调度器（CFS）追求公平，不适合实时任务。
实时内核特点：提供基于固定优先级的抢占式调度策略（如 SCHED_FIFO 和 SCHED_RR）。高优先级任务一旦就绪，会立即抢占低优先级任务。
解决优先级反转：实时内核实现了优先级继承机制。如果一个低优先级任务持有了高优先级任务需要的锁，调度器会临时将低优先级任务的优先级提升到与高优先级任务相同的水平，让它尽快执行完并释放锁，防止被中等优先级的任务“卡住”。
- 4. 高精度定时器（High-Resolution Timers）
普通内核的定时器精度通常受限于系统时钟滴答（Tick，通常是 1ms 到 10ms）。
实时内核特点：深度利用硬件的高精度定时器（hrtimer），提供纳秒级的定时精度。这对于需要严格周期性执行的任务（如工业机器人的电机 PID 控制，要求 100μs 的精确周期）至关重要。
- 5. 内存分配与锁机制的严格限制
为了保证实时性，实时内核不允许任务在执行时发生不可预期的长时间等待。
实时内核特点：在禁用了抢占或中断的上下文中，严格禁止进行可能引起休眠的内存分配（如 GFP_KERNEL），必须使用原子分配或在安全区外分配。此外，像 RCU 回调等机制也会被强制转移到进程上下文（线程）中执行，以避免在硬中断上下文中产生过长的延迟。

# 抢占
- 在普通内核中，自旋锁内的代码是不可抢占的盲区。
- 在实时内核中，锁不再是不可抢占的屏障，系统的响应延迟被压缩到了微秒级。
- 防御性编程的意义：cond_resched() 在普通内核里是防止长循环霸占 CPU 的最后防线；而在实时内核里，由于锁机制的改变，它变得更加可靠，进一步保证了系统的平滑运行。

# linux 抢占
Linux 编译时由 CONFIG_PREEMPT_* 决定。
配置	俗称	内核态能否被抢占
CONFIG_PREEMPT_NONE, 不可抢占内核, 基本不能（除返回用户态等调度点）
CONFIG_PREEMPT_VOLUNTARY, 自愿抢占, 在内核标了「可能睡眠」的路径更易调度
CONFIG_PREEMPT, 完全可抢占内核, 能，除非处于不可抢占区域
## 1. 用户态：始终可抢占
无论哪种配置，用户进程都会被 timer、I/O 完成等事件触发调度。
## 2. 内核态：取决于配置
    - PREEMPT_NONE（不可抢占内核）
内核代码执行中，timer 不会把当前任务强行切走。调度主要发生在：
（1）返回用户态前
（2）显式调用 schedule() / 阻塞式 API（等锁、等 I/O、mutex_lock 等）
    - CONFIG_PREEMPT（完全可抢占，现代主流）
（1）内核线程 / 系统调用路径上，也可以被更高优先级任务抢占
（2）但有很多 不可抢占保护区
## 哪些区域仍然不可抢占
即使开了 CONFIG_PREEMPT，下面仍 不能 被抢占：
- 硬中断 / IRQ handler：不在进程上下文
- preempt_disable() 区间：显式关抢占
- 持 spinlock：关抢占 + 关本地 IRQ（或等价机制）
- local_irq_disable() 临界区：本地 CPU 不响应可屏蔽中断
- 某些 per-CPU 关键段：保证原子性
```
spin_lock(&lock);
/* 临界区：不可抢占 */
spin_unlock(&lock);
/* 之后可能 schedule */
```
可抢占内核，但大量临界区通过关抢占/关中断保证原子性。

# linux 下，一个 tick 长时间，几个 tick 为一个切换时间片？
（1）一个 Tick 是多长时间？Tick（时钟滴答）是 Linux 内核的“心跳”，其时间长度由内核常量 HZ 决定，计算公式为：Tick 长度 = 1 / HZ。
HZ 的值在编译内核时确定，常见的配置有：
- HZ = 100：常见于嵌入式系统，1 个 Tick = 10 毫秒（ms）14。
- HZ = 250：常见于通用桌面系统，1 个 Tick = 4 毫秒（ms）1。
- HZ = 1000：常见于对实时性要求较高的桌面系统，1 个 Tick = 1 毫秒（ms）
（2）几个 Tick 为一个切换时间片？在 Linux 的默认调度器（CFS，完全公平调度器）中，时间片被称为“基础时间片”（base slice）。它的长度是动态计算的，公式为：0.75ms × (1 + log2(CPU核心数))
- 当 HZ = 1000 时：1 个 Tick 为 1ms。对于 1 个 CPU，时间片约为 0.75ms（不足 1 个 Tick）；对于 8 核以上的系统，时间片约为 3ms（即 3 个 Tick）。
- 当 HZ = 250 或 HZ = 100 时：由于 Tick 的精度较低（4ms 或 10ms），进程的实际运行时间通常会远高于理论上的时间片。例如在 HZ=100 时，进程通常会一直运行到下一个 Tick 中断到来时才考虑切换，因此实际消耗的时间片可能是 1 到几个 Tick 不等。
