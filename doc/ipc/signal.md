# 信号（Signal）
## 信号的表示：位图（Bitmask）
在内核中，Linux 使用位图（Bitmask）来记录进程当前的信号状态。
- pending（未决信号集）：记录已经产生但还未被处理的信号。
- blocked（阻塞信号集）：记录进程当前选择屏蔽（忽略/推迟）的信号。
- caught/ignored：记录哪些信号被捕获，哪些被显式忽略。

## 信号的产生（内核注入）
信号可以通过多种方式产生，例如用户按下 Ctrl+C（触发 SIGINT）、调用 kill() 系统调用、或者硬件异常（如除零错误触发 SIGFPE）。当信号产生时，内核会执行以下操作：
- 检查目标进程是否忽略了该信号。如果忽略，直接丢弃。
- 如果进程阻塞了该信号，内核仅将其加入到目标进程的 pending（未决）集合中，不立即处理。
- 如果信号未被阻塞，内核会将该信号加入 pending 集合，并唤醒目标进程（如果它正在睡眠），或者在进程下次从内核态返回用户态时触发处理。

## 信号的递送与处理（核心机制）
信号的实际处理函数是在“用户态”执行的，而不是在内核态。
当进程准备从内核态返回用户态时（例如系统调用结束、中断返回），内核会检查 pending 集合中是否有未被阻塞的信号。如果有，内核会执行以下“偷梁换柱”的操作：
- 修改用户态栈：内核在用户进程的栈上压入一个特殊的结构体（rt_sigframe），里面包含了信号编号、上下文环境（寄存器状态等）以及一个返回跳板（Trampoline）。
- 劫持指令指针（EIP/RIP）：内核将进程返回用户态时的指令指针，强制修改为信号处理函数的入口地址。
- 恢复执行：进程恢复运行时，CPU 以为自己在正常执行代码，实际上直接跳进了信号处理函数。

## 信号的返回（恢复现场）
当信号处理函数执行完毕，通常会调用 sigreturn()（或者通过跳板代码自动调用）。
- 这会触发一次特殊的系统调用，重新进入内核。
- 内核根据之前保存在用户栈上的上下文信息，恢复进程被中断前的寄存器状态。
- 将指令指针改回原来被打断的位置，进程继续像什么都没发生过一样执行。


# 描述一个 signal 的产生、处理到返回的全流程
在 Linux 中，一个自定义捕捉信号（Signal）的完整生命周期，本质上是进程在“用户态”与“内核态”之间进行四次特权级切换的过程。
## 1. 信号产生与保存 (异步阶段)
（1）信号的产生途径主要分为三类，它们最终都会汇聚到内核的同一个处理入口：
- 硬件异常（同步产生）：例如进程执行了除零操作、访问了非法内存地址。CPU 会触发异常中断，陷入内核。内核在异常处理程序中识别出这是进程自身的错误，从而生成对应的信号（如 SIGFPE、SIGSEGV）。
- 外部硬件中断（异步产生）：例如用户在键盘按下 Ctrl+C。键盘控制器触发中断，内核的中断处理程序（ISR）捕获该事件，将其转换为 SIGINT 信号发送给前台进程组。
- 显式的系统调用（异步产生）：进程通过调用 kill()、raise() 或 tgkill() 等系统调用，主动请求内核向自己或指定目标进程发送信号。
（2）内核处理逻辑：内核收到信号后做了什么？
- 第一步：权限与有效性检查。内核会检查发送方是否有权限向目标进程发信号（通常只有 root 或具有相同 UID 的进程才可以），以及目标进程是否存在。
- 第二步：动作预判（丢弃 vs 保存）。内核会查看目标进程对该信号的当前动作配置（是默认动作、忽略还是捕获）：
    - 直接丢弃：如果目标进程配置了“忽略（Ignore）”该信号，或者该信号是 SIGKILL/SIGSTOP 且被错误地尝试忽略，内核会直接丢弃该信号，不占用任何资源。
    - 保存与唤醒：如果信号需要被处理，内核会将其加入目标进程的未决信号集，并检查目标进程的状态。如果目标进程正在深度睡眠（如等待 I/O），内核会调用 signal_wake_up() 将其唤醒，使其进入可运行状态，以便尽快去检查信号。
- 此时，内核不会立即打断进程正在执行的用户态代码，而是等待合适的时机。
## 2. 第一次切换：用户态 → 内核态 (U -> K)
- 触发条件：进程在执行主控制流时，因为系统调用（如 read）、硬件中断（如时间片耗尽触发的时钟中断）或异常，被迫陷入内核。
- 内核动作：内核处理完上述事件（如完成系统调用逻辑），在准备返回用户态之前，会调用 do_signal() 检查 pending 表。如果发现当前信号未被阻塞（不在 block 表中）且处于未决状态，内核决定递达该信号。
## 3. 第二次切换：内核态 → 用户态 (K -> U)
- 内核动作（偷梁换柱）：内核在用户的栈空间上精心构造一个“信号栈帧”，保存当前进程的寄存器状态、栈指针等上下文。随后，内核修改 CPU 的指令指针（EIP/RIP），将其指向用户注册的自定义信号处理函数的入口地址。
- 用户态执行：内核通过 iret 等指令返回用户态。此时，进程并没有回到原来的主控制流，而是直接跳转去执行了信号处理函数（Handler）。
## 4. 第三次切换：用户态 → 内核态 (U -> K)
- 触发条件：自定义信号处理函数执行完毕，遇到 return 语句返回。
- 底层动作：由于内核在构造信号栈帧时，将返回地址设置为了一个特殊的跳板代码（如 glibc 中的 __restore_rt）。因此，return 会触发这个跳板代码，进而执行一个特殊的系统调用 rt_sigreturn（或 sigreturn），使进程第三次陷入内核。
## 5. 第四次切换：内核态 → 用户态 (K -> U)
- 内核动作（恢复现场）：内核执行 sys_rt_sigreturn 处理程序，从之前保存在用户栈上的信号栈帧中，恢复进程原始的寄存器状态、栈指针和指令指针，并清除 pending 表中该信号的标志位。
- 最终返回：内核再次切换回用户态。此时，CPU 的指令指针精准地回到了最初被中断的主控制流位置，进程仿佛从未被打断过一样，继续向下执行代码。


# 问题
## 可以自己给自己发信号吗？
完全可以。 进程自己给自己发信号是 Linux 中非常常见且合法的操作。
```
kill(getpid(), SIGUSR1); // 向自己发送用户自定义信号1
raise(SIGTERM); // 向自己发送终止信号
pthread_kill(pthread_self(), SIGINT); // 向当前线程发送中断信号
```

## 信号发送和投递时机
- 发送（pending）：kill 只把信号记在进程上（sigpending），handler 还没跑。
- 投递（delivery）：信号一般在内核准备返回用户态时投递，安排 handler（或默认动作）生效。
